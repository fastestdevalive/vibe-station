# Revision 5 plan — opus review fixes + mobile title/top-bar/touch-resize

Combines an in-harness opus review's findings (against commit `63dbe983`) with three more items found via live testing on a phone. Fix as much of this as is feasible, prioritized in the order below — critical bugs first, then the medium items (one of which — touch-resize — is the same root cause as new item 12), then the new mobile items, then the dead-code cleanup if time allows.

---

## Critical (fix these first)

**1. Esc is globally hijacked whenever the Files panel is open (which is the default state).** `web-ui/src/components/layout/ToolPanel.tsx:114-126` — a `window`-level `keydown` listener in the **capture phase** calls `stopPropagation()` + `preventDefault()` on Esc whenever `isPanelOpen` is true, which is the default (`fileTreeVisible: true` in `useStore.ts:773`). Confirmed: this eats Esc before it reaches the terminal (breaks Claude Code's Esc-to-interrupt and vim inside the terminal) and before Quick Open's own Esc handler (closes the Files panel hidden behind the dialog instead of closing the dialog). It's also mounted and still swallows Esc even when the tools pane is collapsed or in the `worktreeId={null}` empty state, and with two tools tiles mounted on a canvas both handlers fire and cancel each other (Esc eaten, panel never closes). Fix: scope this to only fire when the Files tool/tools pane is actually focused/relevant (not a bare `window` capture-phase listener that intercepts everything unconditionally), and use `stopImmediatePropagation` semantics deliberately rather than accidentally relying on double-registration. The "second Esc exits fullscreen" half of the original R16 spec was never actually implemented either — implement it or update the docstring, don't leave it claiming behavior that doesn't exist.

**2. The rail's background doesn't fill the tools pane's height.** `ToolPanel.tsx:147-158` — the rail's absolute wrapper isn't a flex container sized to fill, so `.files-left-rail` is only as tall as its icon content (measured: 261px rail inside a 959px-tall tools pane). Below the last icon there's no rail background/border, and preview content shows through that 36px column. Fix the wrapper to actually stretch full height. Also handle rail overflow on short panes (7×34px buttons + divider ≈ 260px minimum) — needs `overflow-y` or equivalent, it currently has none.

**3. Side-panel resize clamps to the *window*, not the tools pane.** `FilesPanel.tsx:121-128,395-396` — width/height max is `min(600, window.innerWidth-80)` / `min(600, window.innerHeight-100)`, not clamped to the tools pane's own actual width/height. Reproduced: dragging in a 578px-wide tools pane can push the panel to nearly 600px, leaving the preview 0px wide and pushing the file-tabs bar off-screen. A persisted width can also end up unreachable if the pane later narrows (split-drag, exiting fullscreen, a mobile stacked split) — only keyboard focus + arrow keys can recover it, and the keyboard-arrow clamp uses a *different* bound (plain 160/600) than the mouse-drag clamp. Fix: clamp against the tools pane's own measured width/height (container-relative, per the original R15 spec), not `window.innerWidth`/`innerHeight`, and make the keyboard and pointer clamps share one function.

## Medium

4. **Resize is mouse-only — no touch support**, `FilesPanel.tsx:353` (only `onMouseDown`) — CSS sets `touch-action: none` but there's no pointer/touch handler, so the panel literally cannot be resized on a touchscreen. **This is the same root cause as new item 12 below (reported live from a phone) — fix both resize handles (the right-edge width handle and the stacked-mode bottom-edge height handle) together as one item.** See item 12 for the recommended approach (Pointer Events API) and a working reference implementation already in this codebase.
5. Persisted `toolPanelTab` of `"devices"`/`"artifacts"` isn't migrated the way `"search"` is (`ToolPanel.tsx:90,233-234`) — a user whose last tab was one of these (from before they were disabled, or via direct state manipulation) lands on a tool with no active rail highlight.
6. No active-highlight on the rail when Files is active but the panel is closed (`FilesLeftRail.tsx:103` requires `fileTreeVisible`). Rail is `role="toolbar"` with no arrow-key nav (R17 was never implemented). VCS's `aria-pressed` switches meaning between "tool active" and "sidebar visible" depending on state — confusing for a screen reader. The VCS rail button's label says "Toggle changed files" even when clicking it would actually switch tools (when Files is active) — fix the label to match what the click will actually do.
7. VCS's own top bar (`.vcs-panel__bar`) is squeezed to a fixed 32px single row, but `.vcs-panel__bar-actions` still has `flex-wrap: wrap` — on a narrow tools pane the actions can wrap and spill over the commit list, or overflow. Give it enough room or drop the wrap in favor of an overflow-safe layout.
8. VCS's commit view still follows the *Files* tool's stacked/side-by-side orientation flag with no way to toggle it independently (ToolPanel only shows the orientation toggle on the Files tab) — stacking Files silently also stacks the VCS commit view. It's also still a real resizable `MasterDetailShell` split there, not the overlay revision 4 was supposed to give it.
9. Ctrl+E now toggles the (hidden, irrelevant) Files flag while on the VCS tab, instead of doing anything to the VCS sidebar — the old `VcsPanel`-specific keyboard effect was removed without an equivalent added for `treeVisibleOverride`.
10. The new global `[data-panel-group] [data-panel] { transition: flex-grow }` rule (`workspace.css:341`, from the collapse-animation work) applies to *every* panel group, including saved-layout restores on worktree switch — while that animates, xterm's resize observer fits roughly every frame, sending a burst of PTY resizes. Confirm this is an acceptable tradeoff or scope the transition more narrowly (e.g. only apply it when a collapse/expand toggle fired it, not on programmatic layout restores).
11. Low-priority: `FilesPanel.tsx:103-106` removes drag listeners on unmount but never calls `onWidthDrag(null)`, so `ToolPanel`'s `dragWidth` can stay stuck overriding the stored width if `FilesPanel` unmounts mid-drag. Low-likelihood (requires unmounting mid-drag), but a one-line fix.

## New — found via live testing on a phone

12. **Side-panel resize handles don't work via touch on a phone** (same root cause as item 4 — fix together). The terminal/agent-pane divider (a `react-resizable-panels` `PanelResizeHandle`) already works fine via touch — that's because the library's handle uses the Pointer Events API internally (unifies mouse/touch/pen in one code path with `setPointerCapture`). `FilesPanel.tsx`'s hand-rolled resize handles (the right-edge width handle, and the bottom-edge height handle added for stacked orientation) only wire `onMouseDown` + `window` `mousemove`/`mouseup`. Rewrite both to use Pointer Events (`onPointerDown`, `pointermove`/`pointerup` listeners, `element.setPointerCapture(pointerId)`) instead of the mouse-specific API — this is a drop-in modernization that adds touch support for free, and is the actual reason the other divider already works. **Bonus, if time allows:** `web-ui/src/components/layout/Layout.tsx`'s own hand-rolled sidebar-width resize handle (`.pane-left-resize-handle`, `startSidebarResize`) has the exact same mouse-only bug — it's desktop-only today so not user-facing on mobile yet, but worth fixing for consistency while touching this pattern, so it doesn't become the next report.

13. **Mobile top-bar title font-size should come down slightly.** Revision 4's fix (making the mobile title `--font-size-xl`, 20px) overshot — reported as "looks very big" on an actual phone. Drop one step to `--font-size-lg` (18px at the mobile breakpoint) in `.top-bar__crumb--mobile-stack` (`workspace.css`, near the rule this revision's plan already touched). Keep the medium font-weight and the brighter color from revision 4 — only the size needs to come down.

14. **Investigate whether the top bar's overall height actually grew on mobile, and restore it if so.** Manual measurement in this session (`.top-bar__row` bounding box at a 390×844 viewport) showed 52px, which is fully explained by the 36px `.icon-btn` (sidebar toggle) plus its `var(--space-2)` top/bottom padding — the same formula would have produced the same 52px *before* revision 4's font-size change too, since even the new 20px/30px-line-height crumb text stays within that 36px+padding envelope, vertically centered. **So this may be a perceived-height change (bigger/bolder text reads as "the whole bar got taller" even though the box didn't), not an actual regression** — but verify this for real rather than trusting the arithmetic above: check out the commit before revision 4's title change, measure `.top-bar__row`'s rendered height on a real mobile viewport, then measure it again on the current code, and compare directly. If there genuinely is a height difference, find the actual cause (a `line-height`/`min-height` interaction this investigation may have missed) and restore the original height while keeping item 13's font-size fix. If the measurements come back identical, say so explicitly in the summary rather than silently changing something — don't "fix" a regression that isn't there.
